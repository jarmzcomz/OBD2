## 1. Project Overview

### Vision
**Auto-Diag Suite** es una herramienta de diagnóstico automotriz para taller y vehículo propio.
Centraliza, sobre un núcleo Python reutilizable, la lectura OBD-II (DTCs y datos en vivo), el
sniffing y decodificación de tráfico CAN/CAN-FD, un cliente UDS (ISO 14229) para diagnóstico
estándar, edición de datos vía flujos diagnósticos legítimos, y un dashboard web local con
logging histórico. Está pensada para mecánicos e ingenieros que trabajan sobre **sus propios
vehículos o con consentimiento del propietario**.

Esta es una herramienta de **diagnóstico y mantenimiento**, no de evasión de seguridad. No
incluye —ni incluirá— Immo Off, cracking de Seed/Key, bypass de HSM/Secure Boot, clonado de
inmovilizador ni manipulación de odómetro.

### Goals
- Leer y borrar DTCs y mostrar PIDs OBD-II en vivo con cualquier adaptador ELM327 o SocketCAN.
- Capturar, decodificar (vía DBC) y exportar tráfico CAN/CAN-FD para análisis offline.
- Ejecutar flujos UDS de diagnóstico (sesiones, lectura de DTC/DID) y escritura **segura** con
  protocolo anti-brick.
- Ofrecer un dashboard local en tiempo real con logging persistente en SQLite.

### Success Metrics
- `pytest` verde sin hardware (bus `virtual` + mock ELM327).
- Dashboard muestra PIDs en vivo por WebSocket contra el simulador.
- Toda escritura UDS bloqueada si no existe un backup verificado por hash.

## 4. Data Model

### Entities

**Session** — una sesión de diagnóstico.
| Field | Type | Notes |
|-------|------|-------|
| id | INTEGER PK | autoincrement |
| started_at | TEXT (ISO) | timestamp inicio |
| vehicle_vin | TEXT | VIN si disponible (mode 09) |
| transport | TEXT | `elm327` / `socketcan` / `doip` |
| notes | TEXT | libre |

**SampleLog** — muestra de PID/señal en el tiempo.
| Field | Type | Notes |
|-------|------|-------|
| id | INTEGER PK | |
| session_id | INTEGER FK→Session | |
| ts | REAL | epoch segundos |
| source | TEXT | `pid` / `can` |
| key | TEXT | nombre PID o señal |
| value | REAL | valor decodificado |
| unit | TEXT | unidad |

**DtcRecord** — código de falla leído.
| Field | Type | Notes |
|-------|------|-------|
| id | INTEGER PK | |
| session_id | INTEGER FK | |
| code | TEXT | e.g. `P0301` |
| status | TEXT | activo / pendiente / histórico |
| description | TEXT | |

**EcuBackup** — respaldo previo a una escritura (Zero-Brick).
| Field | Type | Notes |
|-------|------|-------|
| id | INTEGER PK | |
| session_id | INTEGER FK | |
| ecu_addr | TEXT | dirección lógica |
| did_or_region | TEXT | DID/región leída |
| data | BLOB | bytes íntegros |
| sha256 | TEXT | hash de verificación |
| created_at | TEXT | |

### Relationships
`Session` 1—N `SampleLog`, `DtcRecord`, `EcuBackup`. Toda `EcuBackup` debe existir y verificar
hash antes de permitir una operación de escritura sobre la misma `did_or_region`.

### Database Schema
```sql
CREATE TABLE session (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  started_at TEXT NOT NULL,
  vehicle_vin TEXT,
  transport TEXT NOT NULL,
  notes TEXT
);
CREATE TABLE sample_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id INTEGER NOT NULL REFERENCES session(id),
  ts REAL NOT NULL, source TEXT NOT NULL,
  key TEXT NOT NULL, value REAL, unit TEXT
);
CREATE TABLE dtc_record (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id INTEGER NOT NULL REFERENCES session(id),
  code TEXT NOT NULL, status TEXT, description TEXT
);
CREATE TABLE ecu_backup (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id INTEGER NOT NULL REFERENCES session(id),
  ecu_addr TEXT NOT NULL, did_or_region TEXT NOT NULL,
  data BLOB NOT NULL, sha256 TEXT NOT NULL, created_at TEXT NOT NULL
);
```

## 5. API Design

### Routes Overview
| Method | Path | Description | Auth |
|--------|------|-------------|------|
| POST | `/session` | Crea sesión (elige transporte) | local |
| GET | `/session/{id}/dtc` | Lee DTCs vía OBD-II o UDS | local |
| DELETE | `/session/{id}/dtc` | Borra DTCs (mode 04) | local |
| GET | `/pids` | Lista PIDs soportados | local |
| WS | `/ws/{id}/live` | Stream en vivo de PIDs/CAN | local |
| POST | `/session/{id}/can/capture` | Inicia/detiene captura | local |
| GET | `/session/{id}/can/export` | Descarga `.asc`/`.blf` | local |
| POST | `/session/{id}/uds/read` | ReadDataByIdentifier | local |
| POST | `/session/{id}/uds/backup` | Lee + hashea región (obligatorio pre-write) | local |
| POST | `/session/{id}/uds/write` | WriteDataByIdentifier — **bloqueado sin backup verificado** | local |

### Key Endpoints Detail
- **`POST /session/{id}/uds/write`**: body `{ecu_addr, did, data_hex, backup_id}`. El handler
  llama a `safety.guard.assert_writable(session_id, ecu_addr, did, backup_id)` que verifica que
  exista un `EcuBackup` con `sha256` re-validado contra una relectura fresca. Si falla →
  `409 Conflict` con `{"error": "zero_brick_no_verified_backup"}`. Sólo entonces se ejecuta el
  servicio UDS. Requiere `SecurityAccess` ya concedido con llave legítima del usuario; **el
  sistema no calcula ni adivina llaves**.
- **`POST /session/{id}/uds/backup`**: lee la región/DID, calcula SHA-256, persiste `EcuBackup`,
  devuelve `backup_id`.
- **`WS /ws/{id}/live`**: emite frames `{ts, key, value, unit}` a ~5–20 Hz desde el poller de PIDs.

## 8. Authentication & Authorization
Herramienta **local**: el backend escucha sólo en `127.0.0.1` por defecto. No hay multiusuario.
Si se expone en red de taller, añadir token estático vía variable de entorno `ADS_AUTH_TOKEN`
y middleware simple. Las operaciones de escritura UDS exigen confirmación explícita en UI además
del gate de backup.

## 9. Build Order

**Step 1: Scaffolding**
Crear estructura, `pyproject.toml` (deps: `python-can`, `udsoncan`, `can-isotp`, `cantools`,
`pyserial`, `fastapi`, `uvicorn`, `pytest`), `README.md`, `CLAUDE.md`. `pip install -e .`.

**Step 2: Capa de transporte**
`transport/base.py` (interfaz), `transport/elm327.py` con **modo simulado** (responde PIDs
sintéticos sin hardware), `transport/socketcan.py` (incluye bus `virtual`), `transport/isotp.py`.

**Step 3: OBD-II**
`obd2/pids.py` (tabla + fórmulas), `obd2/dtc.py` (decode P/C/B/U), `obd2/client.py` (leer PIDs,
leer/borrar DTCs). Test: decodificación de PIDs y DTCs.

**Step 4: CAN decode**
`can/sniffer.py`, `can/decoder.py` (cantools + DBC), `can/export.py` (`.asc`/`.blf`).

**Step 5: UDS lectura**
`uds/client.py`, `uds/sessions.py`, `uds/services.py` con ReadDTC y ReadDataByIdentifier.

**Step 6: Storage**
`storage/db.py` + `models.py`: crear esquema SQLite, helpers de inserción/consulta.

**Step 7: Safety / Zero-Brick**
`safety/backup.py` (leer + SHA-256), `safety/guard.py` (`assert_writable` re-valida hash).
Test: la escritura sin backup verificado lanza excepción.

**Step 8: UDS escritura (gated)**
`uds/services.py` WriteDataByIdentifier y rutinas 0x31 documentadas, SIEMPRE detrás de
`safety.guard`. Requiere SecurityAccess concedido con llave del usuario (no se calcula).

**Step 9: Backend FastAPI**
`app/main.py` rutas REST + `app/ws.py` stream WebSocket. `uvicorn app.main:app`.

**Step 10: Dashboard web**
`web/` Vite+React: ConnectionBar, gauges en vivo, DTCPanel, CanMonitor, UdsConsole, LogViewer.

**Step 11: Logging & export**
Persistir muestras y DTCs; export de capturas; LogViewer histórico.

**Step 12: Tests & empaquetado**
Cobertura del núcleo sin hardware; `pytest` verde; build instalable.

**Step 13 (Fase 2): Android**
`android/SPEC.md` → app Kotlin con ELM327 BT que reusa los flujos OBD-II/UDS especificados.

## 16. Reglas No Negociables

1. **Ámbito legal y ético:** la suite es para diagnóstico y mantenimiento sobre vehículos
   propios o con consentimiento del propietario. El README lo declara explícitamente.
2. **Capacidades prohibidas (no implementar nunca):** Immo Off, cracking/brute-force de
   Seed→Key (UDS 0x27), bypass de HSM o Secure Boot, clonado de EEPROM de inmovilizador,
   manipulación de odómetro o de cualquier contador legalmente protegido.
3. **Zero-Brick Protocol:** toda operación de escritura/erase (0x2E, 0x31, 0x34/0x36) exige un
   `EcuBackup` íntegro y verificado por SHA-256 inmediatamente antes; sin él, la operación se
   rechaza. El gate `safety.guard.assert_writable` es obligatorio y no evitable.
4. **SecurityAccess legítimo:** el acceso de seguridad se realiza con llaves que el usuario
   posee por vías legítimas (OEM/contrato). El software nunca calcula, adivina ni fuerza llaves.
5. **Capa física primero:** ante fallos de bus, el diagnóstico asume primero problemas físicos
   (tierra, resistencia ≠ 60 Ω, ruido) antes de la capa de aplicación.
6. **`sim` siempre vivo:** el modo simulado y el bus `virtual` deben funcionar sin hardware para
   que tests y CI pasen en cualquier máquina.
